# 0002. 追跡するリポジトリと、離れ具合の測り方

- Date: 2026-10-29
- Status: Accepted

## Context

追跡するリポジトリを手で列挙すると、Renovate を入れたのに載せ忘れる、やめたのに残る、という
ずれが起きる。Renovate の設定があるかどうかで、追跡する範囲を動的に決めたい。

「最新のリリース」と「離れ具合」は、週次の自動リリース（`plan-release.sh`）と同じ物差しで
測らないと、画面の数字と自動リリースの判断が食い違う。

## Decision

### 追跡の範囲

集計のたびに、GitHub App の installation から見えるリポジトリの一覧を作り直す。次をすべて満たす
ものを追跡する。

| 条件 | 内容 |
|---|---|
| 持ち主 | 設定の `owner` と一致する（大文字小文字は区別しない） |
| fork | fork でない |
| アーカイブ | アーカイブされていない |
| 除外 | 設定の `exclude` に名前（owner なし）が無い |
| Renovate | デフォルトブランチに Renovate の設定ファイルがある |

Renovate の設定ファイルとみなすのは次の場所にあるファイル（blob）である。

- 直下: `renovate.json`・`renovate.json5`・`.renovaterc`・`.renovaterc.json`・`.renovaterc.json5`
- `.github/`: `renovate.json`・`renovate.json5`
- `.gitlab/`: `renovate.json`・`renovate.json5`

`package.json` の `renovate` キーは見ない。調べるにはファイルの中身を読む必要があり、yuanying の
リポジトリでは使っていない。

ファイルの有無は git の tree で調べる（直下の tree を 1 回、`.github` や `.gitlab` があればその
tree をもう 1 回ずつ）。ファイルごとに contents を叩くより呼び出しが少ない。コミットの無い
リポジトリ（GitHub が 409 を返す）は設定が無いものとして扱う。

### 最新のリリース

- git のタグのうち semver のもの（`vX.Y.Z`、`v` なしも可）で、一番大きいもの
- プレリリース（`-rc.1` など）は除く。ビルドメタデータ（`+build.5`）は許し、比較には使わない
- 先頭に 0 のある数（`v01.2.0`）は semver ではないので除く
- 同じ版に `v` ありと `v` なしの両方があれば `v` ありを採る
- 日付は、注釈付きタグならタグを打った日（tagger の日付）、軽量タグならタグが指すコミットの
  committer の日付

タグは `git/matching-refs/tags` で読む。注釈付きか軽量かは、ref が指すオブジェクトの種類で分かる。
`/tags` の一覧ではこれが分からない。

### 離れ具合

- 最新のリリースのタグからデフォルトブランチまでの compare（`<tag>...<default branch>`）の
  コミット数。マージコミット（親が 2 つ以上）は数えない
- そのうち `renovate[bot]` 以外のコミット数。作者の GitHub アカウントが `renovate[bot]` か、
  git の作者名が `renovate[bot]` なら Renovate のものとする（`plan-release.sh` は作者名で見ている。
  アカウントに紐づかないメールで書かれたコミットも取りこぼさないよう、両方を見る）
- GitHub の compare の画面への URL を添える
- 経過日数は、応答を返すとき・メトリクスを読まれるときの時刻とリリースの日付との差。集計の間も
  増えていく

### タグの無いリポジトリ

「未リリース」として一覧に出す。リリースに関する値（タグ・日付・日数・コミット数・compare の
URL）は持たない。

### 並び

既定は、リリースしていない期間の長い順。未リリースを先頭に置き（期間は無限とみなす）、
次にリリースの日付の古い順、同じなら名前の順。

### 測れなかったリポジトリ

一つのリポジトリで GitHub の呼び出しが失敗しても、他のリポジトリの集計は続ける。失敗した
リポジトリも、分かったところまでとエラーを添えて一覧に載せ、その回の集計は失敗とする。
リポジトリの一覧すら取れなかったときは、前回の結果を残す。

## Consequences

- 設定ファイルを足せば次の集計で自動で載り、消せば消える
- リポジトリが N 件あると、1 回の集計で概ね 3〜5N 回 GitHub を呼ぶ。同時に測るのは 8 件までに
  抑え、二次の rate limit を避ける。1 時間に 1 回なら installation の上限（毎時 5,000）には遠い
- compare は base から辿れないコミットを数えるので、タグがデフォルトブランチの外にあると、
  分岐点からのコミットが数に入る
